# M1-T04 知识点讲解：枚举校验 与 事件驱动状态

> 两个知识点都出自 `CustomerFollowServiceImpl.addFollow()`，对着代码看这份文档。

---

## 一、枚举校验：FollowType.of() + BizException

### 1. 问题背景：字符串字段的"脏数据"风险

`follow_type` 在数据库里是 `VARCHAR(16)`，用户传什么都存得进去：

```json
{ "followType": "短信" }
{ "followType": "phone" }
{ "followType": "随便打的" }
```

没人报错——MySQL 对 VARCHAR 来者不拒。但三个月后你想统计"电话跟进的成单率"，SQL 一跑：

```sql
WHERE follow_type = '电话'
```

库里躺着 `PHONE`、`phone`、`电话`、`打电话`——统计直接失真。**字符串字段的自由度是统计的天敌**。

### 2. 解决思路：把"开放填空题"变成"封闭选择题"

`FollowType` 枚举定义了唯一合法的四个值：

```java
public enum FollowType {
    PHONE("电话"),
    VISIT("拜访"),
    WECHAT("微信"),
    EMAIL("邮件");

    private final String label;   // 中文名，给前端下拉框显示用
}
```

前端下拉框只给四个选项，后端再校验一遍——**前后端双保险**，因为前端校验可以被绕过（用 curl 直接调接口）。

### 3. 核心代码逐行拆解

```java
public static FollowType of(String value) {
    for (FollowType type : values()) {          // 遍历四个枚举值
        if (type.name().equalsIgnoreCase(value)) {  // 大小写不敏感比较
            return type;                        // 匹配成功，返回枚举
        }
    }
    return null;                                // 全不匹配，返回 null
}
```

为什么要 `equalsIgnoreCase`：前端传 `phone` 或 `PHONE` 都算对——**宽容输入，严格存储**。存进库的永远是 `type.name()` 规范值。

Service 里的使用：

```java
if (FollowType.of(dto.getFollowType()) == null) {
    throw new BizException("跟进方式只能是电话、拜访、微信、邮件");
}
```

**为什么返回 null 而不是直接抛异常？** 职责分离：枚举只负责"解析"（是不是合法值），Service 负责"决策"（不合法怎么办）。如果枚举里抛异常，它就被绑死在 Web 场景——将来写单元测试、批处理脚本时还得 catch 它。null 是最中立的信号："我解析不了"。

### 4. 完整校验链路（三层防线全景）

```
请求进来
  │
  ├─ 第1层：@Validated + DTO 注解      → 拦"空值"（@NotBlank：followType 不能没填）
  │
  ├─ 第2层：FollowType.of() + BizException → 拦"非法值"（填了，但不在四个选项里）
  │
  └─ 第3层：数据库 VARCHAR(16)          → 兜底长度（超过16字符直接报错）
```

两层校验分工：注解校验**结构性**问题（有没有、长不长），枚举校验**业务性**问题（值合不合法）。有人会问"为什么不用正则 `@Pattern("^(PHONE|VISIT|WECHAT|EMAIL)$")` 一层搞定"——可以，但正则是字符串硬编码，枚举加个值要改两处（正则 + 枚举），迟早不同步。**单一事实源原则**：合法值列表只存在枚举一处。

### 5. 对照其他项目的写法

| 方案 | 优点 | 缺点 |
|---|---|---|
| 本项目：枚举 + of() | 类型安全、有 label、可遍历 | 多写一个方法 |
| @Pattern 正则 | 一行搞定 | 字符串硬编码，双处维护 |
| Spring 的 Converter + 枚举参数 | Controller 直接收枚举 | 全局生效，学习成本高 |

M2 做字典表（`sys_dict`，数据库存的枚举）时你会遇到第三种——运营可改的枚举（比如临时加个"抖音"跟进方式），那时枚举类就不够用了，得查表。**代码枚举管稳定值，字典表管可变值**。

## 二、事件驱动状态：跟进插入 → last_follow_time 刷新

### 1. 问题背景：冗余字段的一致性难题

`last_follow_time` 本来**不用存**——理论上随时能算：

```sql
SELECT MAX(create_time) FROM customer_follow WHERE customer_id = ?
```

但客户列表页每行都要显示"最后跟进时间"，一页 10 个客户 = 10 次聚合查询。列表是高频读，跟进是低频写——**用空间换时间**：把计算结果冗余到 customer 表，读的时候直接拿。

代价：**冗余字段必须跟源数据保持一致**，否则就是"假数据"。谁来维护一致性？——事件驱动。

### 2. 核心思想：事件是"因"，状态是"果"

```
【事件表】customer_follow          【状态表】customer
  记录发生了什么                      记录现在是什么样
  只增不改                            随事件不断刷新
  
  插入一条跟进  ───────触发───────▶   last_follow_time 刷新
       (因)                            (果)
```

这是领域驱动设计（DDD）里 **Event Sourcing** 思想的雏形：状态的每次变化都由事件驱动，状态本身可以被事件回放推导（理论上删掉 customer 表，从 follow 表能重建全部跟进状态）。

你身边的真实例子：

| 事件 | 驱动的状态 |
|---|---|
| 下单支付成功 | 订单状态 → 已支付；库存 → 减少 |
| 用户登录 | last_login_time 刷新 |
| 微信收到消息 | 会话列表置顶 + 未读数 +1 |

### 3. 核心代码逐行拆解

```java
@Override
@Transactional
public void addFollow(CustomerFollowSaveDTO dto) {
    // ① 前置校验：客户必须存在（事件挂在不存在的东西上没有意义）
    Customer customer = customerMapper.selectById(dto.getCustomerId());
    if (customer == null) {
        throw new BizException("客户不存在");
    }
    if (FollowType.of(dto.getFollowType()) == null) {
        throw new BizException("跟进方式只能是电话、拜访、微信、邮件");
    }

    // ② 记录事件
    CustomerFollow follow = BeanUtil.copyProperties(dto, CustomerFollow.class);
    save(follow);

    // ③ 刷新状态：只 set 要改的字段，其余为 null 的字段 MP 不会更新
    Customer update = new Customer();
    update.setId(customer.getId());
    update.setLastFollowTime(follow.getCreateTime() == null ? LocalDateTime.now() : follow.getCreateTime());
    customerMapper.updateById(update);
}
```

三个值得注意的点：

**① 为什么 `@Transactional` 是刚需**：②③ 是两条独立 SQL。没有事务时，若③失败，事件存了但状态没刷——客户显示"最后跟进 8 月 15 日"，实际 8 月 20 日就跟进过了，**数据悄悄说谎**。事务保证两条 SQL 同生共死：要么都成功，要么都回滚。

**② `updateById` 的"部分更新"特性**：MP 默认只更新非 null 字段——`update` 对象只填了 `id` 和 `lastFollowTime`，SQL 是：

```sql
UPDATE customer SET lastFollowTime = ? WHERE id = ? AND deleted = 0
```

不会把 name、level 之类全刷成 null。这个特性叫"选择性更新"，MP 的 updateById 天然支持。**反例警示**：如果你把查出来的 `customer` 整个改了再 updateById，并发场景下会覆盖别人的修改（A 改了电话、B 同时刷新跟进时间，B 的保存把 A 的电话刷回旧值）——所以用"只带两个字段的新对象"做最小更新。

**③ 事务里为什么抛 BizException 能回滚**：Spring 默认只对 `RuntimeException` 回滚，`BizException` 继承自 RuntimeException——又回到当初"为什么继承 RuntimeException 而不是 Exception"那个决策，这里就是它的回报。

### 4. 这个模式的进阶形态（现在不用做，知道即可）

现在"事件驱动状态"是**同步直调**：Service 里手动调 update。当系统变大，同步直调的两个升级方向：

| 升级 | 解决什么 | 依赖 |
|---|---|---|
| Spring 事件（@EventListener） | 解耦：发跟进的人不用知道要刷客户 | 无新依赖 |
| MQ 消息队列 | 削峰 + 跨服务 | Redis/RabbitMQ（超出本项目范围） |

单人项目里同步直调就是最优解——**在合适量级用合适技术**，别过度设计。

---

## 三、两个知识点的连接点

它们其实是一个原则的两面：**数据的可信度是设计出来的，不是碰运气**。

- 枚举校验：保证进来的事件数据可信（garbage in, garbage out 的第一道闸）
- 事件驱动 + 事务：保证推导出来的状态可信
